Answers

1. Which of the five went wrong, and what fixes it?

  • #5 (injection obeyed): the worst result: both owners became admin@example.com. The prompt already says the text is data, and a weaker model ignored it. No prompt fixes this for certain, and a check "is the value in the text?" does not catch it either, because the email is in the text. The real fix is in the design (answer 2) and in the UI: every filled field is marked "suggested" until the user touches it. A cheap extra validation: flag an owner that is the same for every item while the text names other people, and show a warning.
  • #4 (not an agenda): a shopping list became five agenda items, as with Gemini. Fix the schema and prompt: allow items to be empty (or add is_agenda: bool) and say "if the text is not a meeting agenda, return no items"; the UI then shows "No agenda found".
  • #1, #4 (language): "Ukrainian" instead of uk, and "en" for Ukrainian text. Fix the schema: language as a two-letter code with a pattern (^[a-z]{2}$); an invalid value then triggers the retry with the error.
  • #1 (title missed, task text changed): fix the prompt: "the title is the meeting name before the agenda; copy the task text exactly". The user sees and corrects both in the form.
  • #3 (end of week): ambiguous for people too. Fix the prompt with a rule ("end of week" = the coming Friday, or Sunday) and show the resolved date in the form, where the user checks it.

Better than the Gemini run: #2 left the "Hiring plan" owner empty instead of taking the signature, #3 gave a date without inventing 14:00, and starts_at now carries the +02:00 offset.

2. What did input 5 do, and what limits the damage?

Nova 2 Lite obeyed it: both owners were set to admin@example.com (Gemini had ignored it, so the result depends on the model, and a prompt is not a defence). What limits the damage even when the model obeys: the parser only returns JSON, has no database access and no write permission (its role allows only the Bedrock call and logs); the result goes into a form the user reads, with every filled field marked "suggested"; saving goes through the normal API (PUT /meetings/{id}/agenda), which validates it and checks that the meeting belongs to the user. The worst case is a wrong owner in a form that a person checks before saving, and the ai_suggestion stored next to the agenda shows afterwards that the model, not the user, proposed it.

3. What does one parse cost?

Measured with Nova 2 Lite: about $0.0011 per parse (1,470 in, 220 out). 20 organisations × 30 agendas a week × 4.33 weeks ≈ 2,600 parses a month ≈ $2.90 a month. One VPC interface endpoint is $7.30 a month whatever the usage, 2.5 times the whole parsing bill, which is why the parser runs outside the VPC. For comparison, with the same tokens: Claude Haiku 5.5 ≈ $0.00026 per parse ($0.70 a month), Claude Opus 5.5 ≈ $0.010 per parse ($27 a month, more with thinking tokens).

4. 500 saved agendas: is agenda-v2 better than agenda-v1?

Every saved agenda has ai_suggestion (the model's output, model id and prompt_version) next to the final agenda. For each one, compare the two field by field: the share of suggested fields the user kept unchanged (topics, owners, minutes, dates), the number of items deleted, and the number added by hand. Group by prompt_version (and model) and compare the averages, for example "kept unchanged" 0.82 for v1 against 0.89 for v2, with a confidence interval; 500 agendas show a difference of a few points, not a tiny one. Count pastes the user abandoned or cleared completely as a separate failure rate. Before release, run both prompts on a fixed set of inputs, these five included, so that a change in what users paste is not mistaken for a change in quality, and so that #5 is caught before users see it.
